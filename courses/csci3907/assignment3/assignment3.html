Part III: Array-of-structs vs. struct-of-arrays

Think about a (somewhat silly) kindergarten activity where each student is assigned three wooden building blocks, which the teacher keeps in a storage room. Each student is issued an ID number that the teacher will use to access that student's blocks. At any given time, a student can request a block to be retrieved by the teacher. The student can then play with the block, and perhaps modify it by writing on it or painting it a different color, after which the teacher returns it to the storage room.

Imagining what's in the storage room, the students probably think that they each have a box or cubby containing their three blocks, but in reality the teacher has organized the blocks in a way that turns out to be more efficient for storage and retrieval: there is a rack of three shelves, with one shelf for the big blocks, one shelf for the medium-sized blocks, and one shelf for the small blocks, each shelf labeled with the students' ID numbers in ascending order, spaced according to the size of the block on that row.

This made-up example is similar to what we mean by array-of-structs (the more intuitive, cubbyhole approach, that we learn in our Data Structures course and use in our work) versus struct of arrays (rack-of-shelves). In both cases, the less intuitive approach turns out to be more efficient.

Implementing this performance trick in code turns out to be rather simple. We can represent the big blocks as type int (32 bits), the medium-size as type short (16 bits), and the little ones as type char. So your job is to write a program for each approach, and time your two programs on different sizes of N:

  • array_of_structs.cpp should define two little classes: (1) Cubby with a single instance of each datatype, and the appropriate constructors, and (2) StoreRoom, containing an array of N cubbies. Making everything public will simplify your test code.

  • struct_of_arrays.cpp should define just a StoreRoom class, containing an array of N values for each of the three numerical types. Again, making everything public will simplify your test code.
The code that accesses your data can likewise be very simple: inspired by an example in Chapter 2 of the Nanosecond C++ book, I simply wrote a loop of N iterations that added a value (I used the constant 1) to every medium value in my data. Because both programs ran so quickly, I started with N=500,000,000 and went to N=1,000,000,000, in increments of 100,000,000; i.e., five large values of N (ten values being overkill because we're not trying to explore the Big-O concept). As before, run your experiments, record your average times for each condition, and in your writeup include a plot showing your results comparing the times you got for the two approaches.
